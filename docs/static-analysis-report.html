3. 每个模块职责说明

3.1 主工程模块（src/main/java/cn/itcast/demo/mylunarcore）

模块职责
activity活动调度、活动资源配置读取与周期任务触发。
admin后台管理端 Web/API、RBAC 与 Spring Security 配置。
battle战斗领域核心：开战、行动结算、波次切换、结果落库与事件发布。
cache协议响应缓存与可复用包体缓存（如固定响应）。
challenge挑战玩法相关 runtime、仓储与服务封装。
config统一配置模型（端口、TLS、线程、同步策略等）与 Bean 配置。
console控制台命令入口预留（当前文件数为 0）。
domain领域实体模型（玩家、游戏基础对象等）。
event领域事件定义、发布器与监听器（含 battle 事件）。
gacha抽卡系统：卡池配置、保底状态、抽奖算法与奖励发放。
game在线玩家抽象、主循环 Tick 注册与运行支撑。
hotfix热修复资源加载、版本元数据管理。
item物品领域仓储与发放接口，供 gacha/玩法调用。
logging日志分类、统一 logger 封装。
metrics流量/包处理指标采集。
netty网络栈核心：TCP/KCP 启动、编解码、指令注册与分发、协议处理入口。
player玩家会话与登录业务、心跳与登出处理。
reload热加载协调器与资源重载入口。
repository面向游戏/玩家域的 JDBC 仓储实现。
resource静态资源读取与配置资源对象映射。
rogueRogue 玩法相关 domain/runtime/repo/service。
scene场景 runtime 与场景服务。
session会话管理、Channel 属性、Token 绑定与在线状态维护。
sync统一数据同步体系：异步加载、登录推送、周期持久化。

3.2 microservices 模块

模块职责
common/common-api微服务统一响应体与跨服务共享基础模型。
services/api-gateway统一入口网关，负责 HTTPS、服务发现路由、JWT 认证过滤和限流。
services/auth-service登录认证服务：校验凭据并签发 JWT。
services/player-service玩家信息 HTTP 接口示例（已接入注册中心发现）。
services/battle-service已存在构建产物，源码未纳入当前目录（推测为迁移中的战斗微服务）。
docker-compose 基础设施提供 Nacos、MySQL、Redis 作为微服务运行底座。

4. 结论与建议

  • 当前主业务仍以内聚在单体为主，实时协议链路（Netty/KCP）已经形成清晰分层：网络入口 → 命令分发 → 领域服务 → 仓储。
  • 微服务目录处于“迁移脚手架”阶段，建议优先将会话鉴权、玩家读写、战斗结算边界切分后再逐步拆分玩法域。
  • 建议后续补充：跨服务调用链跟踪（traceId）、鉴权下沉、以及 battle-service 源码与单体 battle 逻辑的对齐说明。
