MyLunarCore AI 辅助功能优化方案
基于现有实现代码审查 · 问题诊断与可落地方案 · 2026-07-23
本文档基于仓库当前已落地的 AI 辅助能力（方案 A 规则教练、方案 B LLM+RAG、方案 C 旁路微服务 ai-assist-service、方案 D 战斗启发式/特征采集、方案 E 攻略包）进行代码级体检，列出仍需优化的问题，并给出分优先级的解决方案与落地步骤。原则不变：AI 只读权威状态、可降级、可热更、可审计，不得直接写货币/抽卡/战斗结算。

三、P0：延迟与稳定性（必须先做）
3.1 AskAiAssist 同步阻塞 → 异步回执 + AiHintNotify
现状：AssistPacketHandlers.onAskAiAssist 在业务线程内同步调用 AiAssistApplicationService.ask()，内部可能串行：本地规则教练 → 远程 AiAssistClient.httpClient.send → 本地 LlmAssistGateway.httpClient.send。协议里已有 AiHintNotify，但同步路径几乎不用，仅聊天旁路 askAndNotify 会推送。
解决方案：
协议约定：AskAiAssistScRsp 立即返回 retcode=0 + source=accepted（或保留同步短路径仅给 FAQ/规则）。
将 LLM/远程调用提交到独立 AssistInferenceExecutor（与战斗/登录业务池隔离，队列有界、拒绝策略可降级）。
推理完成后用 channel 事件线程 writeAndFlush AiHintNotify；channel 已断开则只写审计。
超时：超过 llmTimeoutMs/remoteTimeoutMs 推送 source=fallback 的规则答案，retcode 语义对齐 proto 注释中的「4=超时/降级」。
可选双模：配置 syncMode=true 供联调；生产默认 async。
Client --AskAiAssistCsReq--> AssistNettyService  |-- 快速路径：Guide FAQ / 规则教练（<20ms）→ AskAiAssistScRsp  |-- 慢路径：提交 AssistInferenceExecutor         |-- remote / llm         v      AiHintNotify (request_id 关联)
3.2 回答缓存与幂等
现状：同一玩家短时间内重复问「今天做什么」会重复打远程/LLM；无 request_id 幂等。
解决方案：
缓存键：uid + scene + normalize(question) 的 hash；TTL 建议 60–180s；仅缓存 source∈{guide-local,rule,llm,remote-*} 且 retcode=0。
normalize：去空白、全角半角、常见口语同义词映射（「抽卡/卡池」）。
实现可用 Caffeine 本地缓存；多节点后再上 Redis（与配额一并考虑）。
命中缓存时 source 追加 -cache，便于审计区分。
3.3 配额拆分与桶生命周期
现状：AssistQuotaLimiter 用 ConcurrentHashMap 懒建 Bucket，无淘汰；教练提示与 LLM 提问共用 perUidPerMinute=20，高频点「今日建议」会挤掉真正问答配额。
解决方案：
拆分配额：coachPerUidPerMinute（可高，如 60）与 llmPerUidPerMinute（可低，如 10）；日配额 dailyLlmBudget 防刷 Token。
远程成功与本地 LLM 共用「贵配额」，FAQ/规则命中只扣「便宜配额」或不扣。
桶淘汰：Idle 超过 N 分钟移除；或改用弱引用/定时清理，避免长生命周期服内存膨胀。
限流响应带 retryAfterSeconds，客户端可做倒计时提示。
3.4 安全过滤配置化与强化
现状：AssistSafetyFilter / RemoteAssistEngine 硬编码少量正则；隐私探测与充值诱导覆盖面窄；出站命中则整段替换，体验生硬。
解决方案：
将拦截词表落到 data/AssistSafetyRules.json，走 ConfigFileService + 热更，与 CoachTips 一致。
入站分级：block（隐私/违法）/ soft-block（付费诱导提问改官方文案）/ allow。
出站：对「必出」类做句子级替换或拒绝该句，保留其余有用建议；保留长度上限 800。
抽卡场景强制追加官方概率免责声明模板（与 Gacha 文案同源）。
单测扩充：边界语料库（同音、空格插入、英文混写）。
四、P1：回答质量与成本
4.1 RAG：从关键词雏形到混合检索
现状：RagKnowledgeService 用 tokenize + contains 打分；卡池知识块几乎无机制文案；商店仅「商品数」；热更已挂钩 HotReloadCoordinator / ActivityConfigHotReloadService（这点应保留）。
解决方案（分两步）：
Step1（低成本）：丰富 chunk 文本——Banner 写入官方保底说明字段、Shop 写入商品名/货币类型/限购；任务写入目标场景/奖励摘要；切块长度 200–400 字。
Step1：检索加 BM25 或 TF-IDF；同义词词典（主线/任务、卡池/抽卡）；最低分阈值避免噪声召回。
Step2：引入向量索引（本地 ONNX embedding 或 pgvector/RedisSearch），接口仍暴露 search(question,scene,limit)。
混合分：0.6*向量 + 0.4*关键词；scene 加权保留。
引用约束：提示词要求回答必须带 citedConfigIds 中的 ID；否则降级规则文案。
4.2 上下文白名单按场景裁剪
现状：AssistContextBuilder 默认投影 inventory≤128、avatars≤24、talents≤16，再加 globalAvatarUsage；无论问「活动怎么玩」都会塞满上下文，Token 与延迟双高。
解决方案：
按 scene 裁剪：quest→任务+相关材料；gacha→pity/卡池进度；growth→角色属性+天赋；activity→活动列表；meta→使用率；mail→mailSummary。
通用问题仅传 monitoringSummary + activeQuests Top3，避免整包背包。
配置化上限：contextMaxInventorySlots 可按场景覆盖（如 activity=0）。
对 LLM 请求增加 max_tokens / 回答长度提示，控制费用。
4.3 审计与可观测性补齐
现状：AssistAuditService 只把 source=llm 记入 llmHitCount；remote-llm / guide-local / blocked 等未细分；游戏服侧指标未挂到 ServerMetricsMonitor / Micrometer；旁路服务有 /ai/metrics 但游戏服未拉取。
解决方案：
按 source 前缀分类计数：guide-local / rule / fallback / llm / remote-* / blocked / error / cache。
暴露指标：assist_ask_total、assist_latency_ms、assist_llm_tokens_est、assist_quota_reject、assist_remote_error_ratio。
接入现有 ServerMetricsMonitor 周期日志；告警：错误率>5%、P99 延迟>超时阈值、远程连续失败。
审计日志增加 requestId、latencyMs、cacheHit、citedCount；保留脱敏策略。
五、P2：产品体验增强
5.1 GuidePack FAQ 与端侧包完整性
现状：matchGuideFaq 用包含关系+分词加分，阈值 2；toGuidePackProto 的 size 恒为 0；downloadUrl/contentHash 依赖配置但缺少校验与增量更新策略。
解决方案：
FAQ 增加 keywords[]、scene、priority；匹配分 = 问句相似度 + scene 加权。
服务端计算 contentHash（SHA-256）与真实 size；客户端按 hash 决定是否重新下载。
热更推送 GuidePackUpdateScNotify 时带差分版本号；弱网优先本地包。
覆盖率目标：常见 50 问 Local First 命中率 ≥ 40%，显著降 Token。
5.2 多轮会话与引用展示
解决方案：
协议扩展：AskAiAssistCsReq 增加 session_id / client_request_id；服务端保留最近 3–5 轮摘要（仅本 uid，TTL 10min）。
Rsp 强化 cited_config_ids + related_hints 的客户端 UI：可点击跳转任务/活动/商店（复用 action 字段）。
对「接着刚才」类指代，用会话摘要而非完整历史，控制 Token。
5.3 战斗战术提示升级（仍限 PVE）
现状：HeuristicBattleAssistPolicy 固定建议 skillId=1、目标=当前波次第一个存活怪；BattleFeatureCollector 仅落 battleId/playerId/endStatus 等稀疏字段，难以训练策略模型。
解决方案：
短期：威胁评分（剩余 HP、攻击力、精英标记）选目标；按能量/冷却选技能；reason 人可读。
特征采集补齐：波次、敌我血量向量、可用技能、最终操作、胜负；写入 JSONL 保持旁路、不进结算。
接口保持 BattleAssistPolicy，后续可换 ONNX 小模型；PVP 默认禁用。
公平性：模型版本号写入战报；托管需玩家显式开关。
5.4 规则教练内容运营
解决方案：
扩充 CoachTips：体力耗尽、邮件未读、商店刷新、突破材料齐备、热门角色已拥有但未养成等。
tip 增加 cooldownHours / oncePerDay，避免同一提示刷屏。
与活动排期联动：结束前 24h 自动提高 activity tip 优先级。
六、P3：架构收敛与长期能力
6.1 双端逻辑去重
现状：游戏服有完整 Coach/RAG/LLM/Safety；微服务 RemoteAssistEngine 又实现一套规则与安全正则，RemoteLlmGateway 提示词更短、能力不一致。开启 remoteEnabled 时行为可能与本地路径漂移。
解决方案：
目标态：游戏服只做鉴权、配额、上下文投影、协议；推理与 RAG 全集中在 ai-assist-service。
过渡态：抽取 common 模块共享 Safety 规则与 Prompt 模板；微服务成为唯一 LLM 出口。
契约：继续用 common-api 的 AssistAskRequest/Response；增加 schema 版本字段。
网关：api-gateway 已有 ai-assist-service-route，补齐超时/重试/熔断配置。
6.2 用户反馈闭环
新增协议：AssistFeedbackCsReq（request_id、useful、reason_code）。
落库或日志：用于统计有用率、坏案例回放、FAQ 补录。
运营周报：Top 未命中问题、高投诉场景（抽卡/付费）、降级率。
6.3 匹配/阵容推荐（数据成熟后）
复用 AvatarUsageStatsService 与 MatchCompatibilityScorer，输出「已拥有角色中的推荐阵容」。
禁止输出未拥有角色的强诱导抽卡话术；可提示「活动获取途径」类官方配置。

十、结论
MyLunarCore 的 AI 辅助「骨架」已经齐全，当前最大短板不再是「有没有」，而是：（1）慢路径同步占业务线程；（2）RAG/上下文导致质量与成本不稳定；（3）安全、配额、观测仍偏演示级；（4）战斗与旁路服务停留在占位实现。建议严格按 P0→P1→P2→P3 推进：先把延迟与成本打牢，再提升召回与体验，最后收敛架构并形成数据闭环。
落地时继续坚持：只读上下文、失败可降级到规则教练、配置可热更、问答可审计。这样既提升玩家引导体验，又不会破坏战斗结算、经济与抽卡的一致性边界。
